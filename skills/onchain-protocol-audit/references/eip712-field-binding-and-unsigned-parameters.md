# EIP-712 field-binding: the mechanically-proven table, and the class that structurally cannot be fixed

Condensed from a Relay Protocol round that took the long-open `callResolver` digest-malleability
lead and turned it into a **shippable CRITICAL with real numbers** — by replacing "I read the source
and the field isn't in the typehash" with a **forge-generated binding table for every field**, and by
noticing that the winning field was not a struct member at all.

Companions: `live-rpc-forensics-and-eth-call-trap.md` §8 (the ordering rule for signed-struct
hypotheses), §16b (consumer law: an unbound field is only a finding if a consumer fails to re-derive
it), §16c (hash-encoding parity), and `bytecode-dispatcher-forensics.md` §9/§10 (prove the deployed
contract IS this repo before shipping a repo-line finding).

**Section list:** §1 the binding table is generated, not asserted · §2 **the winning class: a
parameter is structurally unexpressible in the digest** · §3 the full field→funds matrix ·
§4 quantify as `INPUT − MIN_OUT` (the victim's own slippage tolerance is the loot) · §5 **the
no-attacker-contract variant is the one that survives triage** · §6 chaining with the surplus
primitive · §7 the griefing direction that does NOT work (and why shipping the negative matters) ·
§8 the allocator bakes tokens — assert the payload, not a balance · §9 severity script ·
§10 **asymmetric-key hash pairs (guard covers a wider field set than the key that is consumed)** ·
§10a the scope question that decides CRITICAL-vs-HIGH for a front-run ·
§10b **the measured answer — no mint, no escrow, a BURN; loot is `quote − MIN_OUT`; CRITICAL demoted to HIGH, plus the replay/floor/batch negatives that close triage's objections**.

## 1. THE BINDING TABLE IS GENERATED BY A TEST, NOT READ OFF THE SOURCE

Reading `hashExecuteAndWithdrawRequest` and listing its arguments is how this lead stayed open for
several rounds: it produces a *belief* about the digest, not evidence, and it is exactly the kind of
belief `live-rpc` §5a warns about (an absence claim with no positive control).

Generate it instead. For each field: build a valid request, compute the digest, mutate **that one
field**, recompute, assert the digests differ. A field that does not move the digest is unbound —
and the test proves it for all fields at once, in one file:

```solidity
function _digest(ExecuteAndWithdrawRequest memory r) internal view returns (bytes32);

function test_bindingTable() public {
    ExecuteAndWithdrawRequest memory base = _validRequest();
    bytes32 d0 = _digest(base);

    // per field: mutate, recompute, assert CHANGE
    ExecuteAndWithdrawRequest memory m;

    m = _copy(base); m.deadline += 1;              assertTrue(_digest(m) != d0, "deadline unbound");
    m = _copy(base); m.minAmountOut -= 1;          assertTrue(_digest(m) != d0, "minOut unbound");
    m = _copy(base); m.fees[0].amount += 1;        assertTrue(_digest(m) != d0, "fee unbound");
    m = _copy(base); m.orderId = bytes32(uint256(1)); assertTrue(_digest(m) != d0, "orderId unbound");
    // … one line per field …
}
```

Result on this target: **13/13 struct fields BOUND.** Every field the earlier rounds had theorised
about (`fees`, `deadline`, `orderId`, recipient, amounts) was in the digest, and the whole
"mutate a signed field" family was dead — **in one test file, not one round per field.**

**Rules that make the table admissible:**

- Mutate **one field at a time**. A multi-field mutation proves "some field is bound", which is
  worthless.
- Assert `digest != d0` **and** print `d0` so the reader sees the same base hash across all rows.
- Keep the negative rows in the file even after they pass. The table *is* the deliverable; it is what
  stops the next session from re-opening `fees`.
- Any field that fails the mutation assert is immediately a candidate §2 question: *did I mutate it
  in a way that survives a copy?* (a `_copy` that shares a dynamic-array reference mutates both —
  it will make every array field look "bound" for the wrong reason).

## 2. THE WINNING CLASS — A PARAMETER IS STRUCTURALLY UNEXPRESSIBLE IN THE DIGEST

The field that broke the target was not a struct member:

```solidity
function execute(
    ExecuteAndWithdrawRequest calldata request,   // ← fully bound (13/13)
    address callResolver,                          // ← a PARAMETER. Not in any typehash.
    bytes calldata callResolverData                // ← a PARAMETER. Not in any typehash.
) external { … }
```

Two consequences, and the second is the one to say out loud in the report:

1. **No `require`/guard can be "missing" here in the usual sense** — there is no field to guard. The
   digest literally cannot cover a value that is not part of the signed struct.
2. **It is unfixable by adding a field to the typehash** (that would be a breaking interface change);
   the fix is to hash the resolver into the digest at `execute()` time or to constrain it against a
   allowlist. This distinction is what turns "a missing check" (informational) into "an architectural
   gap" (high).

**How to find this class — grep the entrypoint signature, not the struct definition:**

```bash
awk '/function execute\(/,/\{/' RelayExecutor.sol        # every parameter, in order
grep -n "abi.encode(EXECUTE_TYPEHASH" -A6 RelayExecutor.sol   # what the digest actually covers
```

Then diff the two lists. Anything in the parameter list and absent from the `abi.encode` is
unsigned. The recurring shapes: a resolver/executor address, a `bytes data` blob, a `uint256`
deadline that is checked *outside* the hash, a `bool` flag that selects a branch.

**The class generalises past this protocol:** any function that takes `(signedStruct, extraArgs…)`
where `extraArgs` steer execution is a candidate. `extraArgs` that only *select among signed values*
are benign; `extraArgs` that choose **where value goes** are the bug.

## 3. THE FIELD → FUNDS MATRIX — the table that decides severity

| field | in digest? | moves funds? | verdict |
|---|---|---|---|
| 13 struct members (`fees`, `deadline`, `orderId`, recipient, amounts, …) | **YES** | yes | dead family — do not re-open |
| `oracle` (parameter) | no | yes | **discountable**: gated by `ORACLE_ROLE`, attacker cannot substitute |
| `callResolver` (parameter) | **NO** | **YES — receives 100% of order input** | **the finding** |
| `callResolverData` (parameter) | **NO** | **YES — arbitrary calls + sweeps** | same finding, second vector |

The `oracle` row is worth keeping: it is the control that shows the table is not just "every parameter
is unsigned therefore everything is broken". One parameter being downstream of a role check is what
makes the `callResolver` row credible rather than alarmist.

## 4. QUANTIFY AS `INPUT − MIN_OUT`, NOT AS "STEALS THE ORDER"

The attacker does not take the whole order value and leave the victim empty — that trips the
slippage guard and reverts. The extractable amount is the **victim's own slippage tolerance**, and
the PoC must show the guard *passing*:

```
digest signed / after resolver swap   : 0xa4566d9b…292a3   ← IDENTICAL
attacker input gain (100% of order)   : 1,000,000,000,000
attacker fill spent (out)             :   999,000,000,000
victim withdraw payload               :   999,000,000,000   ← signed MIN_OUT met, guard passes
attacker net (input − fill)           :     1,000,000,000
```

```solidity
assertEq(digestBefore, digestAfter);                       // the malleability, stated
assertEq(inputToken.balanceOf(attacker), INPUT);           // full input captured
assertEq(inputToken.balanceOf(victim), 0);
assertEq(outToken.balanceOf(victim), MIN_OUT);             // ← victim PAID. guard satisfied.
assertEq(profit, INPUT - MIN_OUT);                          // the actual loot
```

**Print all five numbers.** A triager's first thought on any front-run claim is "the slippage guard
saves them". Showing `victim balance == MIN_OUT` is the single line that kills that objection, because
it demonstrates the guard *did* fire — and was satisfied by the attacker's own choice of payout.

## 5. THE NO-ATTACKER-CONTRACT VARIANT IS THE ONE THAT SURVIVES TRIAGE

First version needed a malicious resolver deployed by the attacker. Real, but reviewers discount it
("requires deploying a contract, that's just MEV with extra steps"). The version that landed uses the
**repo's own shipped resolver** and only attacker-chosen calldata:

```
live quote (GOOD_OUT)             : 1,030,000,000,000
signed floor (MIN_OUT)            :   999,000,000,000
attacker net profit (out units)   :    31,000,000,000
```

Same primitive, **zero attacker infrastructure** — the resolver is already deployed and permissionless
to call. When both variants exist, ship the second as the headline and the first as the explanation;
and check the repo for such a contract before assuming one must be deployed
(`grep -rln "ICallResolver\|CallResolver" contracts/` → the shipped `BasicCallResolver`).

## 6. CHAIN WITH THE SURPLUS PRIMITIVE — one tx, two extractions

If a sibling finding lets the submitter keep the delta between the real fill and the signed minimum,
the two compose rather than compete:

```
input stolen   : 1,000,000,000,000   (C6, via callResolver)
surplus skimmed:    31,000,000,000   (sibling finding)
victim paid    :   999,000,000,000   (attestation met)
```

Build it as an explicit `Z03`-style test that asserts **all three numbers in one tx**. Chained
findings that each assert alone are worth less than one test where both hold simultaneously.

## 7. THE GRIEFING DIRECTION THAT DOES NOT WORK — ship the negative

Attractive mirror of the attack: resolver returns nothing, so the victim's order is blocked.
**It reverts.** The `InsufficientMinimumAmount` check fires, which rolls back the fund pull *and* the
`usedRequests` write:

```
grief: victim input still  : 1,000,000,000,000   ← intact
grief: attacker profit     : 0
grief: victim order fillable: 0
```

Net effect: nothing happening. **Write this down as an explicit negative test**, because the reviewer
will ask for it, and because it is what proves you understand the guard you claimed to bypass in §4.
A guard that *blocks* the griefing direction while *permitting* the profitable direction is the whole
story of this bug in two tests.

## 8. HARNESS TRAP — `RelayAllocator` BAKES the alias token; assert the payload, not a balance

The first PoC draft asserted `receiver.balanceOf(...)` after the allocator call and **failed** — and
the tempting conclusion is "the exploit doesn't work". It does; the assertion was wrong. The allocator
**burns** the spender-alias tokens and records an off-chain payload; the receiver is never credited
on-hub:

```solidity
assertEq(allocator.payloads(hash), expectedPayload);   // ← correct
// assertEq(receiver.balanceOf(...), X);               // ← never happens, by design
```

**Rule:** before asserting a balance in a fork/mirror PoC, read every writer of that balance in the
path. A token that is minted-and-burned inside one call has no post-call balance to assert; the
evidence is the recorded hash. When a test fails, the first hypothesis is the assertion
(`live-rpc` §16g's double-probe law applied to your own harness) — not the exploit.

## 9. SEVERITY SCRIPT FOR THIS CLASS

> **Read §10b before using this table's verdicts.** The round that followed the CRITICAL measured the
> funder (§10a's open question) and the honest severity is **HIGH**, not CRITICAL — the loot is the
> victim's slippage tolerance (`quote − MIN_OUT`), non-replayable, non-batchable, with no mint and no
> solver escrow involved. The table below is the *hypothesis* script; §10b is the measurement.

| Question | This target | Consequence |
|---|---|---|
| Unbound field moves 100% of input? | yes (`callResolver`) | CRITICAL band |
| Guard that should catch it? | `MIN_OUT` — **satisfied**, guard is not a defense | CRITICAL |
| Needs attacker infrastructure? | no (§5 variant) | CRITICAL |
| Needs a privileged role? | no — `execute()` is permissionless | CRITICAL |
| Live code == repo? | **yes, byte-exact** (`bytecode-dispatcher-forensics.md` §9) | CRITICAL stands |
| Replay/multi-order amplifies? | open question when shipping | state it as open, do not assume |

The last row is the honest boundary: a single-order loss is proven, the *aggregate* loss depends on
replay/scale that a separate round must answer. Shipping "CRITICAL, one order per victim, aggregate
unquantified pending replay analysis" is stronger than an unproven "protocol-wide insolvency".

## 10. ASYMMETRIC-KEY HASH PAIRS — when the REPLAY GUARD covers more than the PAYMENT KEY

Found the round after the CRITICAL shipped, on the same protocol, from the same
`_buildPayload` helper that §8 warned about. It is the cleanest sibling of the `callResolver` class:
**the same request is hashed twice, by two different functions, over two different field sets** — and
the guard is keyed on the wider one while the thing being *consumed* is keyed on the narrower one.

```
withdrawRequestHash  = keccak256(abi.encode(params))                    ← includes spender
withdrawParamsHash   = keccak256(abi.encode(chainId, depository, bp))   ← spender dropped
      where bp = BuildPayloadParams{currency, amount, receiver, nonce, data}
```

`spender`/`spenderChainId` are dropped when the allocator builds `BuildPayloadParams`
(`RelayAllocator.sol:401-407`), and `WithdrawParams.hash` hashes exactly that narrower struct
(`GasPaidPayloadBuilder.sol:22-28`). The replay guard can therefore **never** catch a collision,
because the two hashes have different preimages by construction — the requests are legitimately
distinct withdrawals that share one payment record.

**Why this is a distinct class and worth a grep of its own:**

| Pattern | Detection |
|---|---|
| one hash, unbound field | §16b consumer law (does a consumer re-derive?) |
| **two hashes over the same data, different fields** | `grep -rn "keccak256(abi.encode" <file>` and diff the **argument lists** of every hash computed from the same struct |
| a struct assembled for hashing that drops fields | read the *constructor call* of the narrower struct, not the struct definition — the omission is at the call site |

**Impact shape to expect, and how to bound it honestly.** Here the exploit is: attacker submits a
request whose `(chain, depository, currency, amount, receiver, nonce, data)` are byte-identical to a
victim's, with a **different spender** — the victim's gas burn satisfies `_requireGasPaid` for the
attacker's build, and the attacker's alias pays zero. Proven in forge
(`test_U01c_payment_key_omits_spender` PASS: victim burns 100 drops, attacker withdraws 5,000,000
drops with no burn of his own, two `burn` calls, one `gasPayments` entry).

**But the severity is MEDIUM, not Critical, and the reason generalises:** the loss is bounded by the
fee ceiling (`MAX_FEE`, 1 XRP per request) and **no principal moves** — each party's own `amount` is
burned from their own alias. **Cost externalisation ≠ theft**, and a triager will say so. Classify it
as "fee avoidance / cost externalisation, capped at `<fee ceiling>` per request" and put the cap in
the same sentence as the impact.

**The DB-join test for any asymmetric key pair** — before writing a severity word, answer: *who else
can produce a colliding preimage, and what does the collision actually transfer?* If the answer is
"a fee, not principal", it is Medium regardless of how clean the PoC is.

### 10a. THE SCOPE QUESTION THAT DECIDES CRITICAL-vs-HIGH FOR ANY FRONT-RUN FINDING

After the `callResolver` CRITICAL was proven, the obvious next question was *how much does one
attacker take* — and it is **not answered by the PoC's numbers**. A front-run steals the input and
*still pays* the victim `MIN_OUT`; so the severity hinges entirely on one unresolved hop:

> **Who funds the victim's payout — the protocol (mint), a solver's escrow, or the allocator burn?**

| Answer | Severity | Why |
|---|---|---|
| Hub **mints** the payout | **CRITICAL** | loss socialises across all protocol liquidity; cap = total liquidity, not one order |
| a **solver's escrow** pays | **HIGH** | one solver per attack; cap = that solver's inventory |
| **allocator burns** alias tokens and records an off-chain payload (§8) | **MEDIUM/HIGH** | the debit lands on an off-chain ledger; cap = recorded payload |

**Write this as a labelled OPEN QUESTION in the report if it is unresolved** — do not let the PoC's
`INPUT − MIN_OUT` number imply "protocol-wide". The §9 severity table's last row exists for exactly
this, and the round that shipped the CRITICAL left it honestly open. Chasing it is a *new round's*
job: trace `withdraw` from the executor to whoever credits the recipient, and name the contract that
parts with the funds.

### 10b. THE ANSWER, MEASURED — and the CRITICAL it demoted

The follow-up round closed it with three assertions, and the result was **neither of the two
alarming branches**: no mint, no solver escrow, **a burn**. Severity came down to **HIGH**, and the
CRITICAL in §9/§10a was retracted in front of the user.

```
supplyIn   before 1,000,000,000,000 → after 1,000,000,000,000   (unchanged — no mint)
supplyOut  before 6,180,000,000,000 → after 5,181,000,000,000   (DOWN 999e9 — burned)
attacker gain :  31,000,000,000
burned        : 999,000,000,000
venue spend   : 1,030,000,000,000
conservation  : 31e9 + 0 + 999e9 == 1030e9   ✅ no value created
```

**The mechanism, which is worth memorising because it inverts the naive model of the attack:**

```solidity
// _runCalls — the ENTIRE input leaves for the attacker's resolver …
uint256 netInput = HUB.balanceOf(address(this), tokenInId);
HUB.transfer(callResolver, tokenInId, netInput);

// … but _finalizeWithdraw does NOT pay from the oracle. It reads the executor's
// OWN hub balance of the OUTPUT token, and requires the resolver to have filled it:
uint256 withdrawAmount = HUB.balanceOf(address(this), tokenOutId);
if (withdrawAmount < request.outAmountMinimum) revert InsufficientMinimumAmount(...);
_fundSpenderAlias(tokenOutId, withdrawAmount);      // then the allocator BURNS it
```

So the attacker's resolver must **return real output inventory** ≥ `MIN_OUT`. The loot is therefore
**not the order input** — it is the spread between the venue quote and the signed floor:

> `loot = quote(input) − outAmountMinimum` = the victim's entire slippage tolerance.

The victim's "guaranteed payout" is on-chain a **burn** into a spender alias, never a credit to the
receiver — which is exactly §8's assertion trap, now explained causally.

**The three-probe recipe that answers §10a on any fork of this pattern** (all in one forge file,
each asserting a delta rather than a boolean):

| Probe | Asserts | Kills |
|---|---|---|
| no-mint | `assertEq(totalSupply(tokenIn), before)` **and** `assertEq(beforeAfterDiff(tokenOut), MIN_OUT)` | "protocol mints the payout" |
| funder identity | venue inventory delta == 100% of quote; **second solver's balances delta == 0** | "loss socialises across solvers" |
| conservation | `attackerGain + victimOnHubCredit + burned == venueSpend` | "value was created" |

The **second-solver-untouched** assertion is the one that actually decides Critical-vs-High: it is a
single `assertEq(delta, 0)` on a party that is *not* in the attack path, and it is the sentence a
triager needs.

**Scope/multiplier questions, each closed with a negative in the same round** (cheap, and every one of
them was asked in triage):

| Question | Verdict | The one answer that decides it |
|---|---|---|
| Replay the same order? | **NO** | `usedRequests[digest]` is set **before** any transfer — and since `callResolver` is *outside* the digest, a second attempt with a **different resolver collides on the same digest** and reverts `RequestAlreadyExecuted`. The bug defends itself. |
| Attacker chooses a lower floor? | **NO** | `outAmountMinimum` is inside the digest — lowering it → `InvalidSignature` |
| Floor can be **0**? | **YES**, and then extraction is **100%** | no validation anywhere in the oracle/multisig; but 0 is a *signing-policy* risk, not attacker-chosen — say so in that exact framing |
| Batch/Merkle over N orders? | **NO** | one `execute(single)`; Multicall3 wrapping two execs = linear 2×, each needing its own signature |

**The transferable lesson is about severity discipline, not this protocol.** A proven unbound-field
primitive reads like CRITICAL; the honest number is *the victim's slippage tolerance per order*,
non-replayable, non-batchable, with no protocol-wide socialisation. Ship it as **HIGH**, state the
cap formula (`quote − MIN_OUT`), and put the "floor can be 0 ⇒ 100%" caveat in a separate sentence so
it cannot be mistaken for attacker control. The round that demoted its own CRITICAL kept the user's
trust; the alternative was a report that a triager shreds on the first `totalSupply` read.
